## Executive summary

Procurement contract clause review is a Quick win (composite 73): a fixed eight-type clause playbook, six years of executed contracts with redline history as labels, batch latency, and a legal team that already reviews every contract by hand. The build expands the recommended pattern — direct prompting with a structured, enumerated label schema plus per-clause confidence and cited span — into a batch annotation service that pre-marks each inbound contract and routes it to a mandatory counsel review queue. The spine of the plan is the acceptance bar: ≥95% recall on the eight playbook clause types across 150 previously reviewed contracts, with recall deliberately favoured over precision. Every milestone exit criterion ladders toward that bar, measured per clause type rather than in aggregate, because the aggregate hides the minority clause that fails. The system advises and never signs; counsel remains the decision-maker throughout.

## Plan

### Architecture: clause classifier with span citation behind a review queue

**Pattern (echoed, not replaced):** Direct prompting with structured output (fixed label set + confidence). No retrieval or agent machinery is required — the label set is closed at eight playbook clause types (indemnity, liability cap, auto-renewal, data-processing terms, and the remaining four the playbook enumerates).

**Shape of the flow**
1. **Batch intake.** New vendor contracts land in the existing document store. A scheduled job picks up unprocessed documents — batch latency is the stated requirement, so there is no need for streaming or a synchronous API.
2. **Document normalisation.** Convert to text with layout preserved enough to keep clause boundaries and numbering intact; retain character offsets so every prediction can point back to an exact span in the source file.
3. **Segmentation.** Split into clause-level units (heading- and numbering-aware, with overlap at boundaries so a clause split across a page break is not truncated). Segment IDs carry offsets and section headings as metadata.
4. **Classification call.** For each segment, one model call returns a structured object per playbook type: `{clause_type, present: bool, confidence, evidence_span, playbook_rule_id, rationale}`. The label set is enumerated in the schema so the model cannot invent categories. Multi-label is allowed — a single clause can trip more than one playbook rule.
5. **Recall-first thresholding.** Because a miss costs far more than a false flag, the confidence threshold for surfacing a flag is set deliberately low and tuned on the golden set. Anything above the surface threshold goes to the reviewer; anything in a middle band is surfaced but marked "low confidence — verify".
6. **Assembly.** Per-contract annotation record: highlighted spans, the playbook rule cited for each, confidence, and an explicit "no flag found for type X" line so a reviewer can see coverage rather than infer it from absence.
7. **Mandatory human-in-the-loop queue.** Counsel opens the annotated contract, accepts/rejects/adds flags. Nothing reaches procurement as sign-off; the tool's output is an aid to review, not legal advice, and this is stated in the UI.

**Deliberate exclusions for v1:** no vector index or RAG (the playbook is small enough to sit in the prompt or be referenced by rule ID), no agentic tool use, no fine-tuning until prompt-and-schema performance is measured against the bar. The `dataAccess` note in grounding describes a general ingestion-to-index pattern; here the index is unnecessary for classification and only revisited if playbook lookup grows beyond what fits comfortably in context.

**Where a second stage may be needed:** if per-type recall on a specific clause (auto-renewal buried in an exhibit is the usual suspect) fails the bar, add a targeted second pass for that type only — a narrower prompt over a wider window — rather than re-architecting the whole classifier.

**Model and infrastructure choices are capability-stated, not vendor-fixed:** a hosted or self-managed instruction-following model with reliable structured-output support, a job scheduler, an annotation store, and a review UI (which may be a thin layer over an existing legal-ops workflow tool).

### Data pipeline: six years of redlines into a labelled golden set

**Sources (as stated):** six years of executed contracts with legal's redline history; the clause playbook as the labeling rubric. Data readiness scored 4 — the highest-confidence input in this case — but the CRISP guidance applies: readiness scores drop after first contact with the actual files, so hand-inspect a sample before committing to a labelling plan.

**Label derivation.** Redline history is the key asset: where legal struck or amended a clause, that is de facto evidence of a playbook violation. Build labels in two passes:
- *Pass 1 (automated candidate extraction).* Mine redlines and comments for edits touching the eight clause types; align each to the clause span in the executed version. Treat this output as candidates only — an edit may be commercial rather than playbook-driven.
- *Pass 2 (counsel adjudication).* Counsel confirms or rejects each candidate against the playbook rule, and — critically — labels the *absences*: contracts where a clause type was present and acceptable, and where it was genuinely absent. Recall cannot be measured without confirmed negatives.

**Golden set construction.** The acceptance bar names 150 previously reviewed contracts. Stratify that set so each of the eight clause types has enough positive instances to produce a stable per-type recall figure; the minority types (grounding flags systematic misrouting of a minority category as the live risk) need deliberate over-sampling relative to their natural frequency. Include: routine cases, known edge cases (clause hidden in an exhibit or annex, unusual synonyms, cross-referenced definitions), and deliberately hard cases (a clause that looks compliant but fails on one sub-condition). Hold back a slice that is never used for prompt iteration so the final read is not contaminated.

**Confidentiality handling.** Contracts are commercially confidential and internally sensitive. Processing stays inside the approved boundary; counterparty names and pricing are not needed for clause classification and can be masked in any evaluation artefact that leaves the primary store. No contract content is used for model training or retained by an external provider beyond the inference call unless legal has signed off on that specific arrangement.

**Repeatability.** Playbook freshness is periodic, not continuous. Version the playbook: each rule gets an ID and version, and every prediction cites the version it was judged under. When the playbook changes, the affected golden-set labels are re-adjudicated rather than silently inherited. Prep steps (conversion, segmentation, masking) live in a scripted pipeline so a refresh is a rerun, not a manual exercise.

### Evaluation: per-type recall is the only metric that matters

**The bar, restated as the pass condition:** ≥95% recall on the eight playbook clause types across 150 previously reviewed contracts. Recall is prioritised over precision by explicit business decision — a false flag costs a reviewer a minute, a miss costs a lawsuit.

**Layer 1 — Offline evaluation.** Exact-match scoring against adjudicated labels, which classification permits cheaply and objectively. Report **recall per clause type**, never only the aggregate; the pass condition is per-type, so eight numbers must clear the bar, not their mean. Alongside recall, track precision and flags-per-contract as a *load* metric — not a pass/fail gate, but the number that tells you whether reviewers will drown. Also track span accuracy (does the highlighted text actually contain the offending language?) and rule-citation correctness, since a correct label with a wrong citation still costs the reviewer time.

**Layer 2 — Failure taxonomy.** Log every miss into one of: segmentation loss (clause never reached the model intact), reasoning error (clause seen, judged wrong), schema/formatting error, or ambiguous-label (counsel disagrees with counsel). Each has a different fix; conflating them wastes iterations. Ambiguous-label counts are also a signal that the playbook rule needs sharpening rather than the prompt.

**Layer 3 — Red-teaming the known risk.** Targeted adversarial testing against systematic misrouting of a minority clause type: paraphrase clauses into unusual wording, relocate them into annexes and definition sections, split them across sub-clauses, and embed them in unusually long documents. Every finding becomes a golden-set item.

**Layer 4 — Staged rollout measurement.** Shadow mode first: the system annotates, counsel reviews as they always have, and outputs are compared after the fact — this measures live recall without any exposure. Then limited release through the mandatory queue, tracking reviewer agreement rate and reviewer-added flags (a flag counsel adds that the system missed is a live recall miss and the single most important production signal). Full rollout only when the bar holds on live traffic, not just the retrospective set.

**Inter-rater baseline.** Before judging the model, measure how often the two-person legal team agree with each other on golden-set items. If human agreement on a clause type sits below the bar, the bar for that type is a labelling problem first and a model problem second.

**Pre-committed rollback trigger.** Define, before launch, the metric and threshold that pauses the system — the working proposal is: any clause type's rolling live recall falling below the agreed bar over a defined review window, or reviewer-added flags exceeding an agreed rate. The exact window and rate are set with counsel during Phase 1 and written down before shadow mode ends.

### Governance: advisory only, counsel decides, everything attributable

**Oversight is a launch condition.** Grounding states oversight is *required*: every output passes through the counsel review queue before it reaches procurement. There is no auto-approve path in v1 and no 'high confidence' bypass — confidence is a triage aid for ordering the queue, not an authority to skip it.

**Standing disclaimers, enforced in product.** The tool advises and never signs; its output is not legal advice. This appears in the annotation view and on any export, and the annotation record is explicitly labelled as a review aid.

**Confidentiality controls.** Contracts are commercially confidential. Access to the annotation store mirrors existing contract access rights — a procurement manager sees status and cycle time, not another business unit's clause annotations. Log who viewed and who adjudicated each annotation.

**Auditability.** Every annotation records: model/prompt version, playbook rule ID and version, input document hash, confidence, and the reviewer's disposition. Prompts and label schemas are versioned like code so any metric movement is attributable to a specific change — this is the difference between debugging and guessing.

**Failure-mode ownership.** The named risk is systematic misrouting of a minority clause type — a quiet failure, since nobody notices a clause that was never flagged. Countermeasures: per-type recall reported on a fixed cadence to the legal owner; a periodic blind sample where counsel reviews contracts from scratch and results are compared to the system's annotations; and explicit 'no flag found' reporting so a reviewer can see the system considered a type rather than assuming silence means clean.

**Scope discipline.** The system classifies against a fixed playbook. It does not draft replacement language, negotiate, assess commercial terms, or rank vendors. Requests to extend into those areas are new cases requiring their own evaluation.

**Decision rights.** Legal owns the playbook rubric and the acceptance bar. Legal ops owns the pilot and the cycle-time measurement. Procurement is a consumer of outcomes, not a configurer of rules.

### Delivery: thinnest scoreable loop first, then stage the rollout

**Sequencing principle.** Build the smallest version that can be scored against the bar before adding anything. In this case that means: segmentation + one structured classification call + a scoring harness over the golden set. No review UI polish, no dashboards, no second-pass logic until per-type recall is on the table.

**Team shape.** One engineer on pipeline and evaluation harness; one practitioner on prompt and schema design; counsel time reserved for label adjudication and red-team review — the adjudication commitment is the scarcest resource in the plan and should be booked as recurring calendar time, not requested ad hoc. Legal-ops owner accountable for the cycle-time outcome.

**Success measurement matches the budget framing.** The stated pilot success measure is cycle time, not headcount. Instrument time-from-receipt-to-sign-off from day one, including the pre-pilot baseline (median 11 days, ≈6 lawyer-hours per contract, ~20 contracts a month), so the improvement claim rests on measured data rather than impression. At ~20 contracts a month, statistical patience is required: a single month is a small sample, and cycle-time conclusions should be drawn over several months.

**Rollout ladder.** Shadow → limited release behind the mandatory queue → full rollout, with the pre-committed rollback trigger live at each stage. Batch latency means the system can run overnight; there is no need to optimise inference speed in v1, which removes a whole class of engineering work from the critical path.

**Operating cadence after launch.** Weekly during pilot: per-type recall, reviewer-added flags, flags-per-contract, queue time. Monthly: golden-set refresh from new adjudicated contracts, playbook-change review, red-team round on whichever clause type performed worst.

**All durations in the milestone table are estimates**, sized against a two-person legal team with limited adjudication bandwidth, and are listed as assumptions.

### Integration notes

- **Intake.** Hook into wherever inbound vendor contracts already arrive (shared mailbox, contract repository, procurement intake form). Prefer polling the existing store over asking counsel to upload files a second time — a duplicate-entry step will quietly kill adoption.
- **Review surface.** Meet counsel where they already read contracts. If that is a document viewer, deliver annotations as comments/highlights anchored to character offsets; if it is a contract-management workflow, deliver as a structured annotation record against the contract object. Offsets from the normalisation step are what make either possible, which is why they must be preserved at conversion time.
- **Handback to procurement.** Procurement needs status and cycle time, not clause detail. Expose a stage signal ("in legal review", "cleared", "revisions requested") rather than raw annotations.
- **Playbook as data, not code.** Store playbook rules as versioned records with IDs so counsel can amend wording without an engineering release, and so citations stay stable.
- **Reprocessing.** Support re-running a contract under a newer prompt or playbook version, with both annotation sets retained side by side — needed for both audit and evaluation of changes.
- **Degradation behaviour.** If the model call or parse fails, the contract routes to the queue unannotated with a visible "not processed" state. It must never silently appear as a clean contract.

## Data flows

**Batch annotation run (production):** Scheduled job polls the contract store for documents with no current annotation record → Convert to text preserving clause numbering and character offsets; mask fields not needed for classification where the confidentiality policy requires it → Segment into clause-level units with boundary overlap; attach section headings and offsets as metadata → For each segment, one structured-output call returns per-playbook-type presence, confidence, evidence span, rationale and playbook rule ID → Apply the recall-first surface threshold; mark mid-band results as low-confidence → Assemble the per-contract annotation record, including explicit 'no flag found' entries for each of the eight types → Write the record with model/prompt version, playbook version and document hash for audit → Place the contract in the mandatory counsel review queue, ordered by flag severity and confidence → Counsel accepts, rejects, edits or adds flags; disposition is logged against each prediction → Reviewer-added flags are routed automatically into the miss log and golden-set candidate pool → Cleared contract advances to procurement with a status signal only
**Golden set construction and adjudication:** Sample 150 previously reviewed contracts stratified to over-represent minority clause types → Mine redline and comment history for edits touching the eight playbook clause types → Align each candidate edit to a clause span in the executed document → Counsel adjudicates each candidate as playbook violation, acceptable-clause-present, or absent — confirming negatives as well as positives → Measure inter-reviewer agreement per clause type as the labelling-quality baseline → Split into an iteration set and a held-back final-read set → Version and freeze; record playbook version under which each label was adjudicated
**Change and regression loop:** Propose a change to prompt, schema, segmentation or threshold as a versioned commit → Run the full iteration set; report per-type recall, precision and flags-per-contract deltas → Classify any new failures by taxonomy (segmentation loss, reasoning error, schema error, ambiguous label) → Promote only if no clause type regresses below its current level and the target type improves → Run the held-back set only at release candidacy, not during iteration → Add red-team and live-miss findings to the golden set and re-freeze

## Milestones

- **Phase 0 — Lock the bar and the rubric** — Confirm with counsel the eight playbook clause types, their rule IDs and wording, the rollback trigger's exact metric and threshold, and the cycle-time baseline instrumentation. _(~1–2 weeks (estimate))_. Exit: Signed-off playbook v1 with eight enumerated rules, a written rollback trigger, and the recorded pre-pilot cycle-time baseline; acceptance bar restated verbatim as the per-type pass condition.. Risk owner: Legal owner (playbook and bar).
- **Phase 1 — Data contact and golden set** — Turn six years of contracts and redlines into an adjudicated, stratified 150-contract golden set with confirmed negatives. _(~3–4 weeks (estimate), gated on counsel adjudication bandwidth)_. Exit: 150-contract golden set adjudicated by counsel, stratified so every one of the eight clause types has enough positives for a stable per-type recall read, with inter-reviewer agreement measured per type and a held-back final-read slice reserved.. Risk owner: Legal ops (adjudication scheduling); engineer (alignment quality).
- **Phase 2 — Thinnest scoreable classifier** — Segmentation plus one structured classification call plus an automated scoring harness — nothing else. _(~2–3 weeks (estimate))_. Exit: Harness produces per-clause-type recall, precision, flags-per-contract and span accuracy on the iteration set from a single command, with prompt and schema versioned; failures auto-bucketed into the four-category taxonomy.. Risk owner: Engineer.
- **Phase 3 — Iterate to the bar, per type** — Close per-type gaps using threshold tuning, prompt sharpening, segmentation fixes, and a targeted second pass only for any type that resists. _(~3–5 weeks (estimate), dependent on how far the weakest clause type starts out)_. Exit: All eight clause types meet ≥95% recall on the iteration set, with flags-per-contract at a level counsel confirms is reviewable; no type carried by the aggregate.. Risk owner: Practitioner (prompt/schema); legal owner (reviewable-load judgement).
- **Phase 4 — Red team and final read** — Adversarially test the minority-category misrouting risk and take the one clean read on the held-back slice. _(~2 weeks (estimate))_. Exit: Red-team findings logged and folded into the golden set; ≥95% per-type recall holds on the held-back slice under the frozen configuration; any regression documented with its fix and re-read.. Risk owner: Practitioner; counsel as red-team reviewer.
- **Phase 5 — Shadow mode** — Run the system on live inbound contracts while counsel reviews unchanged; compare after the fact. _(~4–6 weeks (estimate), constrained by ~20 contracts/month throughput)_. Exit: Live per-type recall measured against counsel's independent review across the shadow window and consistent with the offline bar; every discrepancy triaged; rollback trigger wired and tested.. Risk owner: Legal ops owner.
- **Phase 6 — Limited release behind the mandatory queue** — Counsel works from pre-annotated contracts through the review queue; track reviewer agreement, reviewer-added flags and cycle time. _(~6–8 weeks (estimate))_. Exit: Bar holds on live traffic with per-type recall reported on the agreed cadence; reviewer-added-flag rate within the pre-committed threshold; cycle-time movement measured against the recorded baseline rather than asserted.. Risk owner: Legal ops owner; legal owner on any pause decision.
- **Phase 7 — Full rollout and operating cadence** — All inbound vendor contracts pre-annotated, with monitoring, monthly golden-set refresh and playbook-change handling in place. _(ongoing)_. Exit: Mandatory review queue in steady-state operation; monitoring dashboard live with per-type recall and reviewer-added flags; documented monthly refresh and playbook-versioning process; rollback trigger active and rehearsed.. Risk owner: Legal ops owner.

## Assumptions & labeled estimates

- All phase durations are estimates, not commitments; they assume a two-person legal team with limited adjudication bandwidth and will shift if counsel time is not reserved in advance.
- Shadow and limited-release window lengths are estimates driven by the stated ~20 contracts/month volume; conclusions about live recall and cycle time need multiple months to become meaningful at that throughput.
- Assumes the clause playbook can be expressed as eight discrete, individually judgeable rules; if a rule turns out to be a family of sub-conditions, it should be split and evaluated separately.
- Assumes redline history is attributable enough to link an edit to a specific clause span in the executed document; if attribution is weak for older contracts, the golden set will lean on more recent years and Phase 1 lengthens.
- Assumes counsel can label confirmed negatives (clause present and acceptable, or genuinely absent), which recall measurement requires; without negatives the bar is not measurable.
- Assumes contracts can be processed within the approved confidentiality boundary and that no contract content is retained for training by any external inference provider without explicit legal sign-off.
- Assumes batch overnight processing satisfies the stated latency need, so no synchronous-inference performance work is on the critical path.
- No accuracy, latency, cost or throughput figures are asserted here beyond the acceptance bar supplied in the grounding; all performance claims must come from the evaluation harness.
- Assumes an existing document store and review surface exist to integrate with; if counsel would need a wholly new workflow tool, that is additional scope not covered by this plan.

## Independent critic audit

**Critic verdict:** SHIP WITH FIXES

**Load-bearing gaps**
- **Threshold tuning contaminates the recall read** — The plan says the surface threshold is "set deliberately low and tuned on the golden set" and Phase 3 closes gaps using "threshold tuning" on the iteration set, but there is no stated rule preventing the threshold from being re-tuned after the held-back read, nor any limit on how many times the held-back slice may be touched if Phase 4 records "any regression documented with its fix and re-read". A re-read after a fix is exactly how a held-back set stops being held back.
- **No precision/load floor makes the bar trivially gameable** — Recall-first is correct, but flags-per-contract is explicitly "not a pass/fail gate" and Phase 3's only load condition is "a level counsel confirms is reviewable" — a subjective judgement with no number. A classifier that flags everything achieves 100% per-type recall and passes every stated exit criterion while destroying the cycle-time outcome the pilot is actually measured on.
- **Segmentation recall is unmeasured as a first-class failure** — "Segmentation loss (clause never reached the model intact)" is listed in the taxonomy, but nothing measures upstream segmentation coverage independently of the classifier. If OCR/conversion drops an exhibit, the miss is attributed downstream and the fix goes to the prompt. Add a conversion/segmentation coverage check (e.g. verify every adjudicated golden-set span survives normalisation) as a Phase 2 exit condition.
- **Rollback trigger thresholds deferred and never rehearsed pre-launch** — Phase 0 exit requires "a written rollback trigger" but the evaluation section says "The exact window and rate are set with counsel during Phase 1 and written down before shadow mode ends" — two different deadlines. Also, "rollback" for a batch advisory tool is undefined: what happens to contracts already annotated and in the queue when the system pauses?
- **No handling of playbook change mid-pilot** — Playbook freshness is periodic and the plan versions rules, but there is no defined behaviour when the playbook changes during shadow or limited release — whether the bar is re-read before the new version goes live, and who authorises running on a version whose golden-set labels are not yet re-adjudicated.

**Top fixes**
- Add a quantified reviewer-load floor (max flags-per-contract or minimum precision per type) as a hard Phase 3 exit gate so the recall bar cannot be met by over-flagging.
- Fix the held-back-set discipline: state exactly which contracts score the bar, that thresholds are frozen before the held-back read, and cap re-reads — the current "any regression documented with its fix and re-read" invites contamination.
- Consolidate the rollback trigger into one deadline (Phase 0) with concrete numbers, and define what pausing means for contracts already annotated or in the queue.

**Overclaims flagged**
- "The label set is enumerated in the schema so the model cannot invent categories" — a schema constrains the output field, not the model's judgement; it prevents out-of-vocabulary labels but is stated as a stronger guarantee than structured output actually delivers, and nothing here prevents mislabelling within the set.
- "this measures live recall without any exposure" (shadow mode) — shadow mode measures recall only against counsel's own review, which the plan elsewhere concedes has imperfect inter-rater agreement; it measures agreement with a fallible reference, not true recall.
- "It must never silently appear as a clean contract" — an appropriate requirement, but stated as an absolute with no mechanism (no fail-closed check or reconciliation between contracts polled and annotation records written) to back it.

**Fabrication scan**
- `a fixed eight-type clause playbook ... (indemnity, liability cap, auto-renewal, data-processing terms, and the remaining four the playbook enumerates)` → ok
- `grounding flags systematic misrouting of a minority category as the live risk` → ok
- `the working proposal is: any clause type's rolling live recall falling below the agreed bar over a defined review window, or reviewer-added flags exceeding an agreed rate` → ok
- `Model and infrastructure choices are capability-stated, not vendor-fixed` → ok
- `~1–2 weeks (estimate)` → ok

**Consistency issues**
- Architecture explicitly discards the grounding's dataAccess pattern ("no vector index or RAG ... here the index is unnecessary") while the CRISP Data Preparation phase in grounding calls for chunking and "metadata that retrieval or routing will filter on". The plan justifies this, but the golden-set/labelling flow never states how playbook rules are actually supplied to the model (in-prompt vs. rule-ID reference) — 'sit in the prompt or be referenced by rule ID' leaves the data flow ambiguous.
- Grounding's offline evaluation layer allows a 50–100 item golden set as an acceptable floor; the plan hard-commits Phase 1 to a fully adjudicated 150-contract set with confirmed negatives plus a held-back slice, effectively creating a larger labelling obligation than grounding contemplates while also using the same 150 for iteration and final read — the held-back slice means fewer than 150 contracts back the actual bar read, yet the exit criteria of Phases 3/4 speak as if the bar (defined over 150) is met.
- Phase 4 exit says "≥95% per-type recall holds on the held-back slice", but a held-back slice carved out of the 150 cannot by itself satisfy a bar defined as "across 150 previously reviewed contracts"; the arithmetic of which contracts the bar is scored on is never reconciled.

**Acceptance bar is the spine:** yes — The bar is restated verbatim in the summary and evaluation section and every milestone exit criterion is expressed as a per-type recall condition (Phase 0 "acceptance bar restated verbatim as the per-type pass condition" → Phase 3 "All eight clause types meet ≥95% recall" → Phase 4 held-back read → Phases 5–6 live recall).
