## Executive summary

Marketing localization QA is a Quick win (composite 81) with no blocking flags: a batch, low-sensitivity classification job over structured strings, with three years of translation memory and a manager correction log already available as labels. The build expands the recommended pattern — direct prompting with an enumerated label schema plus a confidence score — into a batch pipeline that scores every localized string against the nine-locale brand glossary and its source string, then emits a ranked, flagged diff queue per region. The spine is the acceptance bar: catch ≥90% of seeded errors in a held-out set of 500 previously corrected strings while keeping the false-flag rate under 10%, because a noisy queue destroys manager trust faster than a missed error. Deliberately out of scope for v1: retrieval machinery, agentic rewrite suggestions, and any automatic blocking of publication. Humans keep the publish decision; the system only ranks and explains. Because the correction log is the only source of real labels, the largest technical risk is label leakage between the golden set and prompt development — so the held-out 500 is frozen and access-controlled from day one.

**Architecture pattern:** Direct prompting with structured output (fixed label set + confidence)

## Plan

### Architecture

**Pattern (from grounding, unchanged): Direct prompting with structured output (fixed label set + confidence).**

One classification call per (source string, localized string, locale) triple. No retrieval index, no agent loop — the glossary entries relevant to a string are resolved deterministically by term matching before the call and injected as a compact glossary slice. That keeps the prompt small and makes glossary coverage auditable, which retrieval-over-glossary would not.

**Components**
1. *Batch intake* — reads the agency delivery (source + nine locale targets) via a defined read-only tool interface backed by a least-privilege service account. No raw credentials appear in prompts.
2. *Deterministic pre-pass* — cheap, non-model checks that should never consume a model call: target identical to source (untranslated string), empty or placeholder-only target, broken interpolation tokens/placeholders, glossary term present in source but its locale equivalent absent from target. These produce high-precision flags directly.
3. *Glossary slice resolver* — for each string, selects the glossary entries whose source terms appear, plus any locale-specific do-not-translate terms.
4. *Classifier call* — structured output with a fixed enumerated label set. Proposed v1 labels: `clean`, `brand_term_violation`, `untranslated`, `meaning_drift`, `tone_or_register_off`, `placeholder_or_markup_broken`, `ambiguous_needs_human`. Fields returned: `label`, `confidence`, `offending_span`, `glossary_entry_id_or_null`, `one_line_rationale`. Schema-invalid responses are retried once, then routed to `ambiguous_needs_human` — never silently dropped.
5. *Thresholded router* — confidence above the flag threshold enters the manager queue; below it enters a low-priority bucket. Thresholds are tuned per label, because the false-flag budget is not evenly spendable across labels.
6. *Queue surface* — flagged diff view showing source, target, highlighted span, glossary citation, label, and rationale, with accept/reject/edit actions. Every manager action is written back as a label.

**Why not more machinery:** the label set is fixed and the evidence needed per decision fits in a small prompt. Retrieval and agents would add failure modes without addressing the binding constraint, which is precision on `brand_term_violation`.

**Explicitly deferred:** suggested corrections, auto-apply, per-locale fine-tuned models, real-time in-editor checking.

### Data pipeline

**Sources**
- Brand glossary in nine locales — the authority for term correctness. Needs an owner, a version identifier, and a change-notification path; a glossary edit invalidates prior evaluation results.
- Three years of translation memory — the corpus of accepted strings, i.e. the negative (`clean`) class and the source of realistic distractors.
- Regional managers' past correction log — the only real positive labels. Expect it to be inconsistent: free-text notes, mixed granularity, some entries recording style preference rather than error.

**Preparation steps**
1. Pull a hand-inspected sample from each source before writing any pipeline code. Data readiness commonly drops after first contact with the actual files; the grounding scores 4/5 and this step is what confirms or corrects that.
2. Normalize the correction log into a schema of `(source_string, pre_correction_target, post_correction_target, locale, manager_assigned_label, date)`. Where the label is inferable only from free text, have a human assign it against the v1 label set. Log the share of entries that could not be mapped — that share is a real limit on evaluation quality.
3. Normalize glossary entries to `(term_id, source_term, locale, approved_target, do_not_translate_flag, notes)`. Flag ambiguous or conflicting entries to the central brand team rather than resolving them in code.
4. Build the **held-out 500** from previously corrected strings, stratified by locale and by label so no locale or minority label is represented by a handful of items. Freeze it. Store it separately from the development set with access restricted, and record the freeze in version control. Anyone who inspects it during prompt iteration has contaminated it.
5. Build a smaller development golden set (order of 100 items, drawn from the non-held-out corrections) covering routine, known-edge, and deliberately hard cases — this is what prompt iteration runs against.
6. Construct **seeded errors** for locales or labels where real corrections are sparse: take known-clean translation-memory strings and inject controlled defects (swap a glossary term for a plausible wrong variant, revert a segment to source, corrupt a placeholder). Seeding rules are written down and reviewed by the brand team so seeded errors resemble what actually reaches production, not what is easy to detect.
7. Make refresh repeatable: glossary and translation-memory pulls run as a scheduled job with a manifest recording source versions, so a metric movement can be attributed to data, prompt, or model change.

**Data handling:** public marketing copy, no sensitive data, so the constraint is integrity and versioning rather than confidentiality. Still route access through the least-privilege read-only service account described in the grounding.

### Evaluation

**The bar (verbatim, and the pass/fail gate for every change):** catch ≥90% of seeded errors in a held-out set of 500 previously corrected strings, at a false-flag rate under 10% so managers keep trusting the queue.

Both halves are gates. A configuration that reaches high recall by flagging liberally fails.

**Layer 1 — Offline evaluation.** Exact-match scoring against the label set, which is cheap and objective for a classification shape. Report:
- Recall on seeded and real errors, overall and **per label** and **per locale**. The aggregate hides the categories that fail; a minority label collapsing while the aggregate looks healthy is the named risk in this case.
- False-flag rate measured on known-clean strings, computed the way a manager experiences it: flags per 100 strings reviewed.
- Confusion matrix, so `meaning_drift` vs `tone_or_register_off` bleed is visible.
- Threshold sweep curves, so the recall/false-flag trade-off is chosen deliberately and recorded.

**Layer 2 — Human review and red-teaming.** Targeted adversarial work against the identified risk of systematic misrouting of a minority category: near-miss glossary variants, partially untranslated strings, correct translations that merely differ from translation memory, locale variants (e.g. regional spelling differences) that are legitimate. Every finding becomes a golden-set item. Also test the inverse: strings a manager corrected for taste rather than error, which should not be flagged.

**Layer 3 — Inter-rater check.** Before trusting the labels, have two reviewers independently label a sample of the development set. If humans disagree materially on a label, the model cannot be held to a bar on it and the label definition needs sharpening or the label needs merging.

**Layer 4 — Shadow mode on live campaigns.** The system scores real deliveries; managers review as they do today; outputs are compared silently. Compare what the system flagged against what managers actually corrected. This is the only place the false-flag rate is measured against real reviewer behaviour rather than a curated set.

**Layer 5 — Limited release with sampled review**, sampling calibrated to the bar and reduced only as measured accuracy stabilizes on live traffic. Full rollout only after the bar holds on live traffic.

**Pre-committed rollback trigger:** if the observed false-flag rate on live traffic exceeds the 10% ceiling over a defined review window, or per-label recall on the frozen held-out set drops below the bar after any change, the queue reverts to advisory-only (flags hidden, logging continues) pending investigation. The trigger is written down before the first release, not negotiated after.

### Governance

**Oversight model:** spot-check, as specified — a human-in-the-loop checkpoint with sampled review calibrated to the acceptance bar, tightened at launch and relaxed only against measured accuracy. The system never blocks or edits publication in v1; the regional manager remains the decision-maker and the accountable party for what ships.

**Roles**
- *Central brand team* — owns the glossary and the definition of a brand-term violation. Adjudicates disputes between a manager and the system. Owns the seeding rules.
- *Regional marketing managers* — own accept/reject on their locale's queue. Their actions are the ongoing label stream.
- *Delivery owner* — owns prompt/config versions, the frozen held-out set, and the rollback trigger.

**Controls**
- Prompts, label definitions, thresholds, and glossary version are versioned like code; every evaluation run records the exact combination so a metric movement is attributable.
- Every flag is auditable: input string, glossary slice supplied, label, confidence, rationale, threshold in force, and the manager's disposition.
- Glossary changes trigger a re-run of the development golden set before the new version goes live, since glossary edits can silently invalidate prior behaviour.
- Held-out set access is logged. A contamination event means rebuilding the set, not arguing about it.
- Trademark and brand-accuracy decisions escalate to the central brand team; the model's rationale is treated as a pointer for a human, never as an authority on trademark usage.
- Vendor relationship: agency-delivered errors surfaced by the queue should feed the existing localization vendor quality conversation. Decide up front whether flag data is shared with the agency — it changes their incentives and should be a deliberate choice.

**Failure-mode watchlist:** silent degradation after a glossary or model-version change; managers rubber-stamping the queue once they trust it (mitigated by continuing to sample unflagged strings, not only flagged ones); minority-locale recall decay masked by aggregate metrics.

### Delivery

Batch latency and medium volume mean no low-latency serving work is needed — the pipeline runs per campaign delivery, which removes a whole class of engineering cost and is part of why this case scores well on feasibility and time to value.

**Sequencing principle:** build the thinnest version that can be scored against the bar, and resist scope until the core loop is measured. The deterministic pre-pass ships before the model call, because untranslated strings and broken placeholders are among the errors that reached production and they need no model at all.

**Team shape (estimate):** one engineer part-time on the pipeline and queue surface, one localization/brand subject-matter reviewer for label definitions and seeding rules, plus a slice of regional manager time for shadow-mode comparison. Budget is absorbed into existing localization vendor spend, so cost control means avoiding per-string model spend on strings the pre-pass already resolves.

**Definition of done for v1:** the bar holds on the frozen held-out 500; the bar holds through a shadow-mode window on real campaign traffic; the rollback trigger is implemented and tested; per-label and per-locale metrics are visible on a dashboard the brand team can read without asking an engineer.

**Not in v1:** correction suggestions, auto-apply, publication gating, expansion beyond the nine locales, in-editor real-time checks. Each is a candidate for v2 once the queue has earned manager trust.

### Integration notes

- Access to translation memory, glossary, and correction log via read-only database or API access through a least-privilege service account, exposed to the pipeline as a defined tool interface (for example an MCP-style connector). No credentials in prompts.
- The queue surface should live where regional managers already work rather than becoming a tenth tool to check; a review view embedded in the existing localization or campaign workflow, or a per-locale digest with deep links, will out-perform a standalone dashboard on adoption.
- Handoff contract with the agency delivery format needs pinning: file/segment identifiers must be stable enough to map a flag back to a specific string across delivery revisions, otherwise manager dispositions cannot be attributed and the label stream degrades.
- Use a managed model endpoint that supports enforced structured output against a schema; treat provider and model version as versioned configuration so a model update is a change that must re-clear the bar, not a silent event.
- Keep glossary storage as the system of record with a version identifier exposed to the pipeline; do not copy glossary content into prompt templates, or the two will drift.

## Data flows

**Per-campaign batch QA run:** Agency delivery lands: source strings plus nine locale targets, with stable segment identifiers. → Intake job reads delivery and current glossary version via read-only service-account tool interface. → Deterministic pre-pass: untranslated/identical-to-source, empty or placeholder-only, broken interpolation tokens, glossary term present in source with no locale equivalent in target. High-precision flags emitted directly. → Glossary slice resolver attaches relevant glossary entries and do-not-translate terms per string. → Classifier call per remaining string returns structured output: label from the fixed set, confidence, offending span, glossary entry reference, one-line rationale. Schema-invalid output retried once, then routed to ambiguous_needs_human. → Thresholded router applies per-label confidence thresholds: above threshold to the manager queue, below to a low-priority bucket. → Regional manager reviews flagged diffs and accepts, rejects, or edits; publication decision stays with the manager. → Dispositions, labels, thresholds in force, and glossary version written to the audit log. → Nightly metrics job recomputes recall and false-flag rate per label and per locale; breach of the pre-committed threshold triggers the rollback to advisory-only.
**Evaluation set construction and freeze:** Normalize the correction log into structured pre/post pairs with locale and mapped label; record the unmappable share. → Stratify by locale and label; split into a development golden set and the frozen held-out 500. → Seed controlled errors into known-clean translation-memory strings for sparse locales/labels using brand-team-reviewed seeding rules. → Freeze and access-restrict the held-out 500; record the freeze and its manifest in version control. → Every prompt, threshold, or model-version change runs against the development set first, then a single gated run against the held-out set. → Red-team and shadow-mode findings are appended to the development set only, never the frozen set.
**Glossary change propagation:** Central brand team edits a glossary entry; change notification reaches the pipeline owner. → New glossary version is pulled and pinned with a version identifier. → Development golden set is re-run against the new glossary version. → If per-label metrics move materially, the change is reviewed before the version goes live; otherwise it is promoted and the version recorded in the run manifest.

## Milestones

- **Phase 0 — Data first contact and bar lock** — Confirm the glossary, translation memory, and correction log are usable in practice, and lock the acceptance bar and label definitions with the central brand team. _(~1–2 weeks (estimate))_. Exit: Correction log normalized into the v1 label schema with the unmappable share documented; glossary versioned with a named owner; label definitions signed off; inter-rater agreement measured on a labeled sample and judged sufficient to hold a system to the bar.. Risk owner: Delivery owner with central brand team.
- **Phase 1 — Frozen evaluation harness** — Stand up the held-out 500 and the development golden set, plus reviewed seeding rules, before any prompt work begins. _(~1 week (estimate))_. Exit: Held-out 500 built, stratified by locale and label, frozen and access-logged; development golden set of routine, edge, and hard cases in place; seeding rules reviewed by the brand team; scoring harness reports recall and false-flag rate per label and per locale from a single command.. Risk owner: Delivery owner.
- **Phase 2 — Deterministic pre-pass** — Ship the non-model checks that catch untranslated strings, empty targets, broken placeholders, and missing glossary equivalents. _(~1 week (estimate))_. Exit: Pre-pass runs over a full historical campaign delivery; its flags scored against the development set with false-flag rate measured; the subset of past production errors it would have caught is documented.. Risk owner: Engineering.
- **Phase 3 — Thinnest classifier that can be scored** — Add the structured-output classification call with the fixed label set, confidence, span, and rationale, and iterate thresholds on the development set only. _(~2 weeks (estimate))_. Exit: Structured output is schema-valid or safely routed on every item in a full development-set run; per-label and per-locale metrics reported with a documented threshold sweep; prompts and configuration under version control with changes attributable.. Risk owner: Engineering.
- **Phase 4 — Red team and held-out gate** — Adversarially probe the named risk of minority-category misrouting, then take the single gated run at the frozen held-out set. _(~1 week (estimate))_. Exit: Red-team findings added to the development set and addressed; the frozen held-out run meets the acceptance bar — ≥90% of seeded errors caught at a false-flag rate under 10% — with no locale or label falling materially below it in the breakdown.. Risk owner: Delivery owner with central brand team.
- **Phase 5 — Shadow mode on live campaigns** — Run silently on real deliveries while managers review as they do today, and compare system flags against actual manager corrections. _(~2–4 weeks or two campaign cycles, whichever is longer (estimate))_. Exit: Recall against manager-made corrections and false-flag rate measured on live traffic and consistent with the bar; the rollback trigger implemented and deliberately exercised in a test; per-label/per-locale dashboard readable by the brand team without engineering help.. Risk owner: Regional managers with delivery owner.
- **Phase 6 — Limited release with sampled review** — Expose the queue to a subset of locales with sampling calibrated to the bar, and confirm managers act on it rather than around it. _(~2 campaign cycles (estimate))_. Exit: Bar holds on live traffic through the release window; manager accept-rate on flags and time-per-review recorded; no unresolved trust complaint from a participating regional manager; sampling reduction justified by measured stability rather than schedule.. Risk owner: Delivery owner.
- **Phase 7 — Full rollout across nine locales** — Extend to all locales with spot-check oversight as the steady state and glossary-change propagation running as a scheduled job. _(~1–2 weeks (estimate))_. Exit: All nine locales live; bar holding per locale on live traffic; glossary-change re-run automated; rollback trigger and audit log in production; a named owner for the queue's ongoing metrics.. Risk owner: Central brand team.

## Assumptions & labeled estimates

- All phase durations and the two-reviewer/one-engineer team shape are planning estimates, not commitments; they assume data access is granted at Phase 0 and that regional managers can commit review time during shadow mode.
- Assumes the correction log contains enough real error examples per locale and per label to stratify a 500-item held-out set; if not, seeded errors will carry more of the weight and the bar's interpretation should be revisited with the owner before Phase 4.
- Assumes the brand glossary in nine locales is internally consistent enough to serve as ground truth; conflicting entries are escalated to the central brand team rather than resolved in code.
- Assumes agency deliveries carry stable segment identifiers so flags and manager dispositions can be mapped back to specific strings across revisions.
- Assumes 'previously corrected strings' in the acceptance bar means the manager correction log, and that seeded errors constructed from clean translation-memory strings are an acceptable supplement where real corrections are sparse — to be confirmed with the acceptance-bar owner.
- Assumes translation-memory strings not appearing in the correction log can be treated as clean for false-flag measurement; some undetected errors are certainly present in that corpus, which makes the measured false-flag rate slightly pessimistic.
- Assumes the v1 label set is workable; label definitions may be merged or split after the Phase 0 inter-rater check.
- Assumes public marketing copy only, no sensitive data, so no additional data-residency or redaction work is scoped.
- Assumes managed model endpoints supporting enforced structured output are available within existing localization vendor spend; no specific provider is assumed or required.

## Independent critic audit

**Critic verdict:** SHIP WITH FIXES

**Load-bearing gaps**
- **No off-ramp if the held-out gate fails** — Phases 3→4 assume forward motion. There is no defined path for a failed gated run: whether the frozen 500 is rebuilt (and from what, given the correction log is the only real label source), how many gated attempts are permitted, or the decision point at which the case is downgraded from BUILD to a narrower pre-pass-only deployment. Given the plan itself says the correction log may lack enough per-locale positives, this branch is likely, not hypothetical.
- **False-flag rate has no defined denominator or review window** — The bar is "under 10%" and the plan reports it as "flags per 100 strings reviewed," but the rollback trigger says "exceeds the 10% ceiling over a defined review window" without ever defining the window, the minimum sample size, or whether pre-pass flags count toward the model's false-flag budget. As written the trigger cannot be implemented or tested in Phase 5 as the exit criterion claims.
- **Manager-disposition label stream is treated as ground truth without a quality control** — Governance says "Every manager action is written back as a label" and managers' actions are "the ongoing label stream," yet Layer 3 inter-rater checking is applied only once, to the development set at Phase 0. If managers disagree with each other or reject correct flags for taste reasons, the ongoing labels will silently poison future evaluation. No periodic re-audit or adjudication sampling of the live label stream is scoped.
- **No cost ceiling despite cost being a stated constraint** — Budget is "absorbed into the existing localization vendor spend" and delivery says "cost control means avoiding per-string model spend," but there is no per-campaign string volume estimate, no per-run cost envelope, and no threshold at which model spend becomes a reason to re-scope. Cost is asserted as controlled rather than bounded.

**Top fixes**
- Define the failure branch of the held-out gate: how many gated runs are allowed, what rebuilding the frozen 500 requires if contaminated or failed, and the explicit condition under which v1 is reduced to the deterministic pre-pass only.
- Make the false-flag metric operational: fix the denominator (which strings count), the review window, the minimum sample, and whether pre-pass flags count — then restate the rollback trigger and its restart condition so Phase 5's "deliberately exercised" exit criterion is achievable.
- Label or delete the unsupported predictions — the embedded-view adoption claim, "destroys manager trust faster than a missed error," "high-precision flags," and "never silently dropped" — and add a recurring inter-rater/adjudication audit of the live manager label stream rather than a one-time Phase 0 check.

**Overclaims flagged**
- "a review view embedded in the existing localization or campaign workflow ... will out-perform a standalone dashboard on adoption" — an unmeasured prediction stated as fact.
- "the rollback trigger implemented and deliberately exercised in a test" as a Phase 5 exit criterion, when the trigger's threshold window and denominator are never specified — it cannot be exercised as an implemented rule.
- "These produce high-precision flags directly" (deterministic pre-pass) — precision is asserted before the Phase 2 measurement that would establish it; the pre-pass's own glossary-equivalent-absent check is plausibly noisy for morphologically rich locales.
- "Schema-invalid responses are retried once, then routed to ambiguous_needs_human — never silently dropped" — an absolute guarantee that ignores intake failures, timeouts, and strings never scored at all.

**Fabrication scan**
- `a review view embedded in the existing localization or campaign workflow, or a per-locale digest with deep links, will out-perform a standalone dashboard on adoption` → must-label
- `because a noisy queue destroys manager trust faster than a missed error` → must-label
- `which makes the measured false-flag rate slightly pessimistic` → must-label
- `Use a managed model endpoint that supports enforced structured output against a schema` → ok
- `**Team shape (estimate):** one engineer part-time on the pipeline and queue surface, one localization/brand subject-matter reviewer` → ok

**Consistency issues**
- The evaluation section allows only "a single gated run against the held-out set" and states "Anyone who inspects it during prompt iteration has contaminated it," yet Phase 4's exit criterion demands the run "meets the acceptance bar" with a per-locale/per-label breakdown — the plan never says what happens if that single gated run fails, which is the most likely branch and would consume the frozen set.
- Data flow step "Nightly metrics job recomputes recall and false-flag rate per label and per locale" is not supported by the rest of the plan: after limited release, ground truth for unflagged strings only exists if managers keep reviewing them, and recall against manager corrections is described as a shadow-mode-only measurement. Nightly recall is not computable as stated.
- Phase 4 raises the gate above the grounding bar ("with no locale or label falling materially below it") without defining "materially" or getting the acceptance-bar owner to re-lock that stricter bar — an undefined pass condition on the decisive milestone.
- The rollback trigger reverts the queue "to advisory-only (flags hidden, logging continues)" — with flags hidden, this is effectively a full shutdown of the user-facing value, not an advisory mode; the naming understates the impact and no restart criterion is given.

**Acceptance bar is the spine:** yes — The bar is quoted verbatim as "the pass/fail gate for every change" and drives Phase 1 (frozen held-out 500 stratified by locale/label), Phase 4 ("≥90% of seeded errors caught at a false-flag rate under 10%"), Phase 5/6 (bar holds on live traffic), and the rollback trigger.
**Verdict integrity:** pass — Plan states verdict BUILD, matching the grounding, and reproduces composite 81, Quick win, classify shape, spot-check oversight, and the acceptance bar verbatim without softening either half. Scope is narrowed rather than inflated ("Deliberately out of scope for v1"), so no rosier drift.
