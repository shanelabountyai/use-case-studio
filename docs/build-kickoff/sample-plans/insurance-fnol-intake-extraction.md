# Build Kickoff — process (BUILD) · v1

> **Decision-support, not a guarantee.** This plan was generated by a bounded LLM pipeline from your evaluation inputs. It is a defensible starting point, not a validated design — every estimate is labeled and must be checked against reality. ## Executive summary

FNOL intake is a Quick win (composite 70): high-value, decent data readiness, and the hard part is integration rather than modelling. The build is an orchestrated multi-step workflow — deterministic ingest, normalisation, and validation steps, with LLM extraction only where the source is unstructured (call transcripts, free-text email, scanned PDF forms). Every extracted field carries a confidence value; policy numbers are validated against the policy master as a deterministic gate; anything sub-threshold is routed to the intake coordinator's review queue. The acceptance bar (≥97% field accuracy on a 400-claim labeled set, full routing of sub-threshold fields, policy-number validation before acceptance) is the spine: it is what the golden set measures, what shadow mode must reproduce on live traffic, and what the rollback trigger watches. Human review is a launch condition, not a phase-two nicety, because oversight is stated as required and the data is regulated. Plan for the integration and audit-trail work to dominate effort; the extraction model itself is the smaller risk.

## Plan

### Architecture

**Pattern (from grounding): Orchestrated multi-step workflow — deterministic pipeline with LLM steps where judgment is needed.**

Stages, each with an explicit checkpoint and a persisted intermediate artefact:

1. **Intake adapters (deterministic).** Three channels: telephony recordings/transcripts, email (body + attachments), and PDF forms (native and scanned). Each adapter normalises to a common `submission` envelope: channel, received timestamp, raw artefact pointer, checksum, tenant/state jurisdiction.
2. **Document conversion (deterministic).** OCR/text layer extraction for PDFs and images, transcript retrieval for calls. Store page/segment offsets — these are the anchors for the audit trail.
3. **Redaction/masking pass (deterministic).** Mask fields the extraction step does not need (e.g. full bank details, medical narrative where not required for triage) before any content reaches a model; log what was masked and why.
4. **Field extraction (LLM step).** Structured output constrained to the target schema: policy number, loss date, loss type, estimated severity — plus per-field source span (page/segment + character offset) and a per-field confidence signal. Use a fixed output schema with validation; reject and retry once on schema violation, then route to review.
5. **Deterministic validators.** Policy number checked against the policy master via a read-only service-account lookup; loss date checked for plausibility against policy effective/expiry dates and submission date; loss type mapped to the controlled vocabulary used by the claims system; severity constrained to the defined bands. A field that fails a validator is forced to review regardless of model confidence.
6. **Confidence routing.** Per-field thresholds (calibrated in Phase 2, not guessed) decide auto-accept vs review. Any single sub-threshold or validator-failed field sends the whole claim to the queue with only that field flagged, so reviewers correct rather than rekey.
7. **Review queue UI.** Side-by-side source document with highlighted source spans and the proposed value. Reviewer accepts, edits, or rejects; the edit is captured as a label.
8. **Claims-system write.** Single idempotent write path keyed on submission id, only after acceptance (auto or human). Failed writes park in a retry queue with alerting — never silently drop a claim.

**Retrieval component.** A vector index over the 18 months of historical FNOL submissions plus form-template exemplars supports few-shot selection and template recognition ("this looks like Carrier X's fax form"), with metadata filters on channel, form type, and jurisdiction. Frequent re-indexing on the source's update cadence; result freshness stamped. A managed vector store or an index inside the existing data platform are both acceptable — capability, not product, is the requirement.

**Latency.** Interactive from the coordinator's perspective: the coordinator opens a submission and sees proposed fields. Where OCR/transcription is slow, run extraction asynchronously on arrival so the fields are usually pre-computed by the time the queue item is opened; the UI must handle the not-yet-ready state explicitly.

**Explicitly out of scope for v1:** severity estimation beyond the defined bands, coverage determination, reserve setting, any customer-facing communication.

### Data & Pipeline

**Ground truth.** 18 months of FNOL submissions paired with the keyed-in claims-system records. Treat these keyed records as *noisy* ground truth — the stated problem is that intake rekeying produces typos, so some disagreements between model and record will be the record being wrong. Adjudicate every disagreement in the labeled set by hand against the source document; that adjudication is what makes the 400-claim set trustworthy.

**Building the 400-claim labeled set.** Stratify deliberately rather than sampling at random: by channel (phone/email/PDF), by form template, by jurisdiction/state, by loss type (including the long-tail types), and by known-hard characteristics (scanned-and-faxed, handwriting, multiple loss dates mentioned, policy number absent or partial, third-party reporter). Two independent labelers on a subsample to measure inter-labeler agreement; if humans disagree materially on a field, the field definition needs fixing before the model is blamed.

**Preparation steps.** Convert and de-skew scans; strip carrier boilerplate and email signature/disclaimer blocks; segment call transcripts by speaker turn; retain page and offset metadata throughout so every extracted value is traceable to a span. Metadata for filtering: channel, form template id, jurisdiction, received date, submitting party type.

**Access pattern.** Read-only access to the policy master and the historical claims records through a least-privilege service account, exposed to the workflow as a defined tool interface (for example an MCP-style connector) — never raw credentials in prompts, never write access from the extraction path. The claims-system write is a separate, narrowly scoped credential used only by the acceptance step.

**Retention.** State-level retention rules govern the raw artefacts, the extracted fields, the model inputs/outputs, and the review decisions. Get the retention matrix from compliance before designing storage, because it determines whether prompt/response logs can be kept at all and for how long. Assume raw documents and derived fields may have different clocks.

**Feedback loop.** Every reviewer edit becomes a candidate label; a weekly triage adds the interesting ones to the golden set and tags failure category (OCR/transcription miss, retrieval miss, extraction reasoning error, schema/formatting error, validator gap). Growth of the golden set from production failures is expected and budgeted.

### Evaluation

**The bar (verbatim):** ≥97% field accuracy on a 400-claim labeled set, with every sub-threshold field routed to review; policy numbers validated against the policy master before acceptance.

That is three separate tests and all three must pass:

1. **Field accuracy.** Report per-field accuracy *and* the aggregate, because a 97% aggregate can hide a weak field. Define exact-match rules per field type up front: policy number exact after normalisation; loss date exact to the day; loss type exact against the controlled vocabulary; severity exact band. Also report a claim-level "all fields correct" rate — it is the number adjusters actually feel, and it will be lower than the field-level number.
2. **Routing completeness.** Every field whose confidence sits below its threshold, and every field failing a validator, must appear in the review queue. Test this as a property with injected low-confidence and validator-failing cases, not by inspection.
3. **Policy-number validation.** No acceptance path may exist that bypasses the policy-master lookup. Verify by attempting it in a test harness.

**Threshold calibration.** Confidence thresholds are derived, not chosen: plot per-field accuracy against confidence on the labeled set and set each threshold where auto-accept accuracy clears the bar with margin. Publish the resulting auto-accept coverage — the share of fields that clear threshold — as the efficiency metric, kept strictly separate from the accuracy metric so nobody trades one for the other quietly.

**Scoring method.** Extraction fields are largely deterministic to score. Where judgment enters — severity banding, ambiguous loss-type mapping — use a written rubric applied by humans on a sample; LLM-as-judge may scale it only after judge–human agreement is measured on a subsample and found acceptable. Judge–human agreement is an empirical question, not an assumption.

**Red-teaming.** Targeted adversarial testing against the identified risk (prompts engineered to extract sensitive records): documents containing embedded instructions, attachments crafted to make the extractor emit content from other claims, attempts to make the model return policy-master data it was not asked for. Also test cross-claim leakage in the few-shot retrieval path — retrieved historical exemplars must not surface another claimant's details into an output field. All findings become golden-set entries.

**Staged rollout.** Shadow mode (system extracts, coordinators keep rekeying, outputs compared silently) → limited release on selected channels/templates with the mandatory review queue → full rollout only when the bar holds on live traffic. **Pre-committed rollback trigger:** rolling field accuracy on live sampled traffic falling below the bar for a defined window, reviewer override rate on auto-accepted fields exceeding its agreed ceiling, or any confirmed cross-claim data-leak incident — any one pauses auto-accept and reverts all fields to review.

### Governance & Risk

**Human oversight is a launch condition.** Every claim passes the review queue before it reaches the claims system in the limited-release phase. Auto-accept for high-confidence, validator-passing fields is unlocked only after the bar holds in shadow and limited release, and even then sub-threshold fields and validator failures always route to a human. Adjusters inherit whatever intake produced, so the queue is the only place errors get caught cheaply — make review fast and evidence-rich rather than optional.

**Auditability.** The compliance requirement is that every automated extraction is traceable to its source document. Persist, per field: source artefact id and checksum, page/segment and character span, model and prompt version, retrieval context ids, confidence value, threshold in force, routing decision, reviewer identity and action, timestamp. This record must be reconstructable for the full state-mandated retention period and reproducible for a regulator or in a coverage dispute. Prompts and configuration are versioned like code so that any metric movement is attributable to a specific change.

**Data protection.** Regulated insurance data: redaction before model calls, least-privilege read-only access to the policy master, no PII in telemetry or error logs, encryption in transit and at rest, and a documented decision on whether any content may leave the controlled environment. If a hosted model is used, the data-handling and retention terms must be reviewed and recorded before the first production document is processed.

**Ownership.** A named business owner for the acceptance bar and the thresholds; a named engineering owner for the pipeline and the rollback switch; compliance sign-off on the retention matrix and audit-record design before limited release. Model/prompt changes require a golden-set run and owner approval — no silent prompt edits in production.

**Known risks to watch.** Noisy ground truth inflating or deflating measured accuracy; OCR quality on faxed/handwritten forms driving most residual error; template drift as carriers and partners change forms; automation bias in reviewers who start rubber-stamping — instrument reviewer agreement and override rates as ongoing metrics, and sample-audit auto-accepted fields indefinitely.

### Delivery

**Shape of the work.** The largest line item is integration, not model work — that is consistent with the funding assumption and should drive staffing. Expect roughly: pipeline and claims-system integration engineering as the bulk, data/labeling effort for the golden set, a smaller share for prompt and threshold work, plus a review-queue UI. All durations below are **estimates** and should be re-baselined after Phase 1's hands-on data inspection.

**Team.** One integration engineer (claims system, policy master, telephony/email intake), one ML/pipeline engineer, a claims SME who owns field definitions and adjudicates labels, a part-time front-end contributor for the review queue, and compliance as a reviewer at defined gates.

**Sequencing principle.** Build the thinnest workflow that can be scored against the bar before adding channels. Suggested order: PDF forms of the highest-volume template first (most structured, easiest to validate), then email free text, then call transcripts — transcription quality is the least controllable input and should not gate the first measurement.

**Instrumentation from day one.** Per-field accuracy on sampled live traffic, auto-accept coverage, reviewer override rate, queue latency, write-failure rate, retrieval freshness. Dashboard these before limited release, not after.

### Integration Notes

- **Claims system write path.** Idempotent, keyed on submission id, with an explicit reconciliation report so a coordinator can prove every received submission reached a terminal state (accepted, in review, or parked with an error). Confirm whether the claims system exposes a suitable API or whether the write must go through an existing intake interface — this answer materially changes the effort and should be settled in Phase 1.
- **Policy master lookup.** Needs a normalisation layer for policy-number formats (spacing, prefixes, legacy schemes) and a defined behaviour for near-misses: propose the candidate to the reviewer rather than auto-correcting.
- **Telephony.** Establish who owns recordings and transcripts, what consent/retention applies, and whether transcripts are available in near-real time or on a lag; the interactive latency expectation depends on this.
- **Email.** Attachment handling, threaded/forwarded submissions, and duplicate detection (the same FNOL arriving twice by different channels) need explicit rules; duplicates are a common source of downstream mis-triage.
- **Jurisdiction routing.** State-level retention differences mean jurisdiction must be resolved early in the pipeline, since it affects where artefacts are stored and for how long.
- **Existing rekeying process.** Keep it operable throughout shadow and limited release; the rollback trigger is only credible if the manual path is still warm.

## Data flows

**Submission → structured claim fields:** Intake adapter receives phone transcript, email, or PDF and creates a submission envelope with checksum and jurisdiction → Document conversion produces text with page/segment offsets preserved → Redaction pass masks fields not needed for extraction; masking log persisted → Retrieval fetches similar historical submissions and matching form-template exemplars with metadata filters → LLM extraction returns policy number, loss date, loss type, estimated severity, each with a source span and confidence signal → Deterministic validators run: policy master lookup, date plausibility against policy dates, loss-type vocabulary mapping, severity band check → Confidence routing splits fields into auto-accept candidates and review-required → Reviewer sees source document with highlighted spans, accepts or edits flagged fields → Accepted record written idempotently to the claims system; audit record persisted with model/prompt version, spans, confidences, and reviewer action
**Reviewer edit → golden set:** Reviewer edit captured as a candidate label with the original model output → Weekly triage tags failure category (OCR/transcription, retrieval, extraction reasoning, schema, validator gap) → Selected cases adjudicated against the source document by the claims SME → Case added to the golden set with stratification metadata → Next candidate change re-run against the expanded set before release
**Historical corpus → retrieval index:** 18 months of FNOL submissions loaded from the document store → Conversion, boilerplate stripping, and chunking with offsets retained → Metadata attached: channel, form template id, jurisdiction, received date, party type → Embeddings written to the vector index; freshness stamp recorded → Scheduled re-indexing on the source update cadence; new templates flagged for review
**Live monitoring → rollback:** Sampled live extractions compared against reviewer decisions and periodic manual audit → Per-field accuracy, auto-accept coverage, and reviewer override rate computed on a rolling window → Threshold breach or confirmed leakage incident fires the pre-committed trigger → Auto-accept disabled; all fields revert to mandatory review → Failure cases enter the golden set; re-enable requires a passing golden-set run and owner approval

## Milestones

- **Phase 1 — Lock the bar and meet the data** — Confirm field definitions with the claims SME, inventory access to the historical corpus and policy master, and hand-inspect a stratified sample of real submissions across all three channels. _(2–3 weeks (estimate))_. Exit: Written field-definition spec agreed by the business owner; access granted to historical records and the policy master via least-privilege service account; sample inspection report documenting actual document quality (OCR legibility, transcript quality, template variety) and any downward revision to feasibility assumptions; claims-system write interface confirmed.. Risk owner: Business owner (field definitions) and integration engineer (access).
- **Phase 2 — Golden set and thinnest workflow** — Build the adjudicated 400-claim labeled set and the minimal deterministic-plus-LLM pipeline for the highest-volume channel, with validators and per-field confidence in place. _(4–5 weeks (estimate))_. Exit: 400-claim stratified set adjudicated against source documents with inter-labeler agreement measured on a subsample; pipeline produces schema-valid output with source spans and confidence for every field; policy-master validator wired and un-bypassable in the test harness; first per-field accuracy baseline reported against the ≥97% bar.. Risk owner: ML/pipeline engineer, with claims SME owning label quality.
- **Phase 3 — Calibration, channel coverage, and red-teaming** — Calibrate per-field confidence thresholds, extend to email and call transcripts, and run adversarial testing including cross-claim leakage in the retrieval path. _(3–4 weeks (estimate))_. Exit: ≥97% field accuracy on the 400-claim set with per-field breakdown published; thresholds derived from accuracy-vs-confidence curves with auto-accept coverage reported separately; 100% of sub-threshold and validator-failed fields demonstrably routed to review under injected test cases; red-team findings triaged and added to the golden set with no unresolved leakage issue.. Risk owner: ML/pipeline engineer and compliance reviewer.
- **Phase 4 — Shadow mode on live traffic** — Run the workflow silently alongside existing rekeying; compare outputs against coordinator-keyed results and audit disagreements. _(3–4 weeks (estimate))_. Exit: Live sampled field accuracy holds at the bar with no auto-accept enabled; every disagreement with coordinator output adjudicated and categorised; audit record verified reconstructable end-to-end for a sampled set of claims; compliance sign-off on retention matrix and audit design; rollback trigger metrics and thresholds signed off by the named owners.. Risk owner: Business owner (go/no-go) and compliance.
- **Phase 5 — Limited release behind mandatory review** — Route selected channels/templates through the review queue as the working intake path, with reviewers correcting flagged fields instead of rekeying. _(4 weeks (estimate))_. Exit: Bar holds on live traffic across the release scope; reviewer agreement and override rates instrumented and within agreed ceilings; write-path reconciliation shows every submission in a terminal state; manual rekeying path retained and demonstrably operable as rollback.. Risk owner: Claims intake operations lead.
- **Phase 6 — Auto-accept and full rollout** — Enable auto-accept for high-confidence, validator-passing fields, extend to remaining channels, and establish the ongoing audit and golden-set growth cadence. _(ongoing after 3–4 weeks (estimate))_. Exit: Auto-accept enabled only for fields whose calibrated accuracy clears the bar with margin; sub-threshold and validator-failed fields still 100% routed to review; continuous sample audit of auto-accepted fields running; weekly failure triage feeding the golden set; rollback trigger live and tested.. Risk owner: Business owner, with engineering owner holding the rollback switch.

## Assumptions & labeled estimates

- All phase durations are estimates only and must be re-baselined after Phase 1's hands-on data inspection; no schedule commitment is implied.
- The stated volume of ~400 claims a week and ~7 minutes of rekeying per claim are the case's own figures, carried forward unverified; no new throughput, latency, accuracy, or cost figures are introduced by this plan.
- Keyed-in claims-system records are assumed to be usable but noisy ground truth; the plan assumes every model/record disagreement in the labeled set is hand-adjudicated against the source document.
- Access to the policy master via a read-only least-privilege service account is assumed obtainable; if it is not, the policy-number validation requirement in the acceptance bar cannot be met and Phase 2 stalls.
- A programmatic or supported write interface into the claims system is assumed to exist; confirming this is a Phase 1 exit item because the plan's effort profile depends on it.
- Call transcripts are assumed available for phone-channel FNOLs; if transcription must be built or is of poor quality, that channel is deferred rather than allowed to gate the first accuracy measurement.
- Per-field confidence thresholds are assumed derivable from the labeled set; they are calibrated in Phase 3, not pre-specified here.
- State-level retention rules are assumed obtainable as a documented matrix from compliance before storage design is finalised.
- Reviewer capacity is assumed sufficient to handle 100% review during shadow and limited release; if not, rollout scope is narrowed rather than review being waived.
- Technology choices are described as capabilities (managed vector store, tool-interface connector, hosted or self-hosted model); no specific vendor or product is mandated.

## Independent critic audit

**Critic verdict:** SHIP WITH FIXES

**Load-bearing gaps**
- **No defined path if the ≥97% bar is missed** — Phase 3's exit criterion is "≥97% field accuracy on the 400-claim set" but refineGate is null and no milestone states what happens on failure — per-field remediation loop, scope narrowing to a subset of fields/channels, or a no-go decision. Add an explicit stop/refine branch owned by the business owner.
- **OCR/transcription quality has no acceptance gate of its own** — Governance flags "OCR quality on faxed/handwritten forms driving most residual error" and the failure taxonomy includes "OCR/transcription miss", yet no phase measures conversion accuracy independently. Extraction accuracy will be blamed for upstream conversion loss. Add a per-channel conversion-quality metric and a minimum threshold before a channel enters extraction scope.
- **Unhandled failure modes in the write and duplicate paths** — Duplicate detection is deferred to "need explicit rules" in Integration Notes but appears in no milestone exit criterion, and the retry queue for "Failed writes" has no defined max-age, escalation owner, or SLA. Both are silent-corruption routes into the claims system.
- **Audit-trail retention conflicts not resolved before build** — Governance requires persisting "model and prompt version, retrieval context ids, confidence value" while Data & Pipeline concedes retention "determines whether prompt/response logs can be kept at all". If compliance forbids prompt/response retention, the auditability design breaks — this must be settled in Phase 1, not at Phase 4 sign-off.
- **Cross-claim leakage risk from the retrieval path is tested but not architecturally constrained** — Red-teaming tests that "retrieved historical exemplars must not surface another claimant's details", but the architecture offers no structural control (e.g. redacted/synthetic exemplars, template-only retrieval) — testing alone is a weak control for a regulated-data leak.

**Top fixes**
- Reconcile Phase 6 auto-accept with the grounding's unconditional HITL launch condition: state explicitly that auto-accept is a post-launch change requiring business-owner and compliance approval, with the criteria and the oversight-requirement interpretation written down.
- Add an explicit failure branch for the ≥97% bar (refine/narrow-scope/no-go) plus an independent OCR/transcription quality gate per channel, so conversion loss is not silently charged to extraction accuracy.
- Label invented specifics as proposals or estimates — team composition, weekly triage cadence, "expected and budgeted" golden-set growth — and soften absolutes ("un-bypassable", "never silently drop a claim") to what the design and tests actually support.

**Overclaims flagged**
- "policy-master validator wired and un-bypassable in the test harness" — a harness test shows no bypass was found on tested paths, not that none exists; state it as "no bypass path found under adversarial test".
- "Failed writes park in a retry queue with alerting — never silently drop a claim" — an absolute guarantee the design does not underwrite (no retry ceiling, dead-letter owner, or reconciliation SLA is specified).
- "the extraction model itself is the smaller risk" — inferred from a budget line item ("largest line item is integration"), not from any feasibility evidence; feasibility scores 3 and the plan itself flags OCR/handwriting as the dominant error source.
- "red-team findings triaged and added to the golden set with no unresolved leakage issue" — implies leakage can be closed out, when the plan provides no structural containment, only tests.

- `One integration engineer (claims system, policy master, telephony/email intake), one ML/pipeline engineer, a claims SME ... a part-time front-end contributor for the review queue` → must-label
- `Growth of the golden set from production failures is expected and budgeted.` → must-label

**Consistency issues**
- The grounding's HITL clause is unconditional — "every output passes through a review queue before it reaches its destination — the stated oversight requirement makes this a launch condition, not an option" — but Phase 6 "Enable auto-accept for high-confidence, validator-passing fields" removes the human from a share of outputs. The plan never reconciles this with oversight=required; it only cites the acceptance bar's narrower sub-threshold clause.
- Validator design assumes policy-master attributes the access assumption does not cover: "loss date checked for plausibility against policy effective/expiry dates" requires effective/expiry data, while the assumption only secures "Access to the policy master via a read-only least-privilege service account" for policy-number validation.
- Latency is declared interactive but partly deferred: "run extraction asynchronously on arrival so the fields are usually pre-computed" plus the Integration Note that transcripts may be "on a lag" leaves no stated latency budget or measurable target for the interactive requirement.
- Instrumentation lists "queue latency" and reviewer capacity is assumed sufficient, yet no milestone exit criterion measures whether 100% review of ~400 claims/week is actually absorbable before Phase 5 goes live as the working intake path.

**Acceptance bar is the spine:** yes — The bar is decomposed into three testable clauses in Evaluation and each recurs as a milestone exit criterion — Phase 2 "policy-master validator wired and un-bypassable", Phase 3 "≥97% field accuracy ... 100% of sub-threshold and validator-failed fields demonstrably routed", Phase 5/6 "Bar holds on live traffic" — and it also defines the rollback trigger.
**Verdict integrity:** pass — Plan states BUILD, matching grounding, and does not inflate: it repeatedly warns of noisy ground truth, integration dominance, and possible "downward revision to feasibility assumptions" in Phase 1.
