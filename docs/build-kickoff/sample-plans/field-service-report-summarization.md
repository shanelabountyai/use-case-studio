## Executive summary

Field technicians dictate voice notes; an admin retypes them the next morning, losing detail and weakening warranty claims. The build turns each voice note into a structured, pre-filled work-order summary (parts used, fault found, follow-up needed) that the technician confirms on the same visit. The architecture is direct prompting grounded with RAG over reference material: the parts catalogue and two years of note/work-order pairs supply the correct part numbers and house phrasing, while the model composes the summary into fixed fields. The spine of delivery is the acceptance bar — ≥90% field-level accuracy against 200 admin-verified work orders, with no fabricated part numbers, every part validated against the catalogue. Because part numbers are the highest-consequence field, they are constrained by deterministic lookup rather than left to generation. Oversight starts as sampled human review calibrated to that bar and tapers only as measured accuracy holds. Batch latency means transcription and drafting can run asynchronously, which removes most performance pressure and lets the team spend its effort on accuracy and grounding instead of infrastructure.

## Plan

### Architecture

**Pattern (from grounding): Direct prompting grounded with RAG over reference material.**

Flow, thinnest viable version first:

1. **Capture** — technician's dictated note lands in a queue (existing recording workflow, unchanged at first). Batch latency is accepted, so no streaming path is needed.
2. **Transcription** — a speech-to-text capability converts audio to text. Expect site-specific vocabulary problems (part nicknames, equipment models, accents, generator/compressor noise). Keep the raw transcript stored alongside the audio reference so every downstream field is traceable.
3. **Retrieval** — two grounding sources, queried separately:
   - *Parts catalogue* via read-only lookup through a defined tool interface (exact/fuzzy match on part name, model, description). This is a database lookup, not embedding similarity, because part numbers demand exact resolution.
   - *Reference work orders* via a vector index over the two years of note→work-order pairs, filtered by metadata (equipment type, fault category, customer site type) to inject house style and typical fault phrasings.
4. **Composition** — direct prompting produces the structured summary against a fixed field schema: parts used, fault found, work performed, follow-up needed, warranty-relevant observations. Output is schema-constrained (typed fields, enumerations where they exist), not free prose.
5. **Part-number gate** — a deterministic post-step. Every part the model proposes must resolve to a catalogue entry. Unresolved candidates are emitted as `unverified: "<technician's words>"` for the technician to pick from a shortlist. The model is never the authority on a part number; the catalogue is.
6. **Confirmation UI** — technician sees the pre-filled draft on the same visit, edits, confirms. Confirmed output writes to the work-order system; the edit delta is captured as evaluation signal.

**Deliberately out of scope for v1:** agentic multi-step planning, fine-tuning, automatic closure without technician confirmation, real-time in-ear drafting. Data readiness scored 3 — the first version exists to find out how good the transcripts and note/order pairs actually are.

**Prompt and config discipline:** prompts, field schema, retrieval parameters and model settings are versioned like code so any metric movement is attributable to a specific change.

### Data & Retrieval Pipeline

**Sources:** two years of dictated notes with matching completed work orders; the parts catalogue as a lookup table.

**First action is manual inspection, not engineering.** Pull a sample of roughly 50 note/work-order pairs and read them by hand. Data readiness scored 3, and the specific questions to answer are: does the archive contain the original *audio*, or only the admin's retyped text? Are notes reliably linked to their work order, or is the join fuzzy? Do work orders record parts by catalogue number, or by free-text description? Each answer changes the build.

**Preparation steps:**
- *Pair curation* — build a clean corpus of (note text → final work order) pairs. Discard pairs where the linkage is uncertain; a noisy reference corpus poisons retrieval and evaluation alike.
- *Field extraction from history* — parse the historical work orders into the same field schema the system will emit. This is what makes field-level accuracy measurable.
- *Chunking & metadata* — reference work orders chunked at the record or field-group level (not arbitrary character windows), tagged with equipment type, fault category, site type, and date so retrieval can filter to comparable jobs.
- *Catalogue normalisation* — build a lookup surface over the parts catalogue: canonical part number, description, common aliases and technician nicknames harvested from the historical notes. This alias table is the single highest-leverage artefact in the build, because it is what turns "the big blue filter" into a real part number.
- *Repeatable refresh* — catalogue and reference corpus refresh on the source's update cadence (data freshness is periodic), through a scripted pipeline, not a manual re-upload.

**Access pattern:** read-only access through a least-privilege service account, exposed to the model as a defined tool interface. No raw credentials in prompts. Customer site addresses are commercially sensitive — they are retrieved and displayed but excluded from any general-purpose reference corpus unless required for the field, and stripped from evaluation exports.

**Known failure sources to instrument from day one:** transcription errors on part names, notes that genuinely lack the information a field asks for (the correct output is "not stated", not a guess), and multi-visit jobs where one note spans several work orders.

### Evaluation

**The bar, unchanged:** ≥90% field-level accuracy against 200 admin-verified work orders; no fabricated part numbers, verified against the parts catalogue.

**Golden set construction.** Assemble the 200 admin-verified work orders with the service-desk admin who currently does the transcription — they are the only person who can adjudicate ambiguity. Composition should be deliberate, not random: routine single-fault visits, known edge cases (multi-part jobs, no-fault-found visits, follow-up required, poor audio), and hard cases (unfamiliar equipment, technician using nicknames only, note that contradicts the eventual work order). Start scoring as soon as a first tranche of 50–100 is ready rather than waiting for all 200.

**Two distinct metrics, scored separately — do not average them:**
1. *Field-level accuracy* — per-field correctness against the admin-verified reference, reported per field. An aggregate that hides a weak "follow-up needed" field behind a strong "fault found" field is useless for prioritising fixes.
2. *Part-number fabrication* — a hard gate. Any emitted part number that does not resolve to a catalogue entry is a failure regardless of field accuracy. Measure it as a count, tracked to zero-tolerance on the golden set, and enforce it in code via the deterministic gate rather than relying on the model's behaviour.

**Scoring method.** Structured fields (part numbers, follow-up flags, enumerated fault categories) are scored exactly by comparison. Free-text fields (fault description, work performed) need rubric scoring: a written rubric — is it factually supported by the note, is it complete, is it in house style — applied by humans on a sample. LLM-as-judge may scale this, but only after judge-versus-human agreement is measured on a subsample; agreement is an empirical result, not an assumption.

**Failure taxonomy.** Log every miss as retrieval miss (catalogue/alias gap), transcription error, reasoning/inference error, hallucinated detail, or formatting/schema error. Each has a different fix, and the first version's distribution across these categories determines where effort goes next.

**Red-teaming.** Explicit adversarial passes: notes that mention a part but say it was *not* used; notes referencing a part number that has been superseded in the catalogue; deliberately garbled audio; notes where the technician speculates about a fault. Every finding is added to the golden set permanently.

**Live signal.** Once technicians are confirming drafts, the edit delta between draft and confirmed work order is a continuous, no-extra-effort accuracy proxy. Track it per field and watch for drift after any catalogue or prompt change.

### Governance & Oversight

**Human-in-the-loop, as grounded:** start with sampled human review calibrated to the acceptance bar; reduce sampling only as measured accuracy stabilises. Oversight level for this case is spot-check, and the technician confirmation step is a structural control, not an optional convenience — the system never closes a work order unaided in v1.

**Layered controls:**
- *Deterministic part validation.* The catalogue gate sits outside the model. Unresolved parts surface as explicit unverified candidates with a pick-list, never as a plausible-looking number. This is the control that addresses the fabrication clause in the acceptance bar.
- *Abstention over invention.* Fields the note does not support must be emitted as empty or "not stated". Rubric scoring penalises confident filling of absent information more heavily than an honest blank.
- *Sampled admin review.* The service-desk admin reviews a defined sample of confirmed work orders weekly against the rubric during early operation, tapering as per-field accuracy holds. Sampling rate changes are a recorded decision, not a drift.
- *Traceability.* Every field links back to the transcript span and the retrieved catalogue/reference record that supported it. Warranty claims are the commercial payoff here, so provenance matters when a claim is contested.

**Data handling.** Customer site addresses are commercially sensitive; sensitivity is internal and no consumer PII is involved. Access via least-privilege read-only service accounts; addresses excluded from evaluation exports and from any shared reference corpus. Recording retention follows existing service-operations policy — confirm it covers audio, since the current process may treat voice notes as ephemeral.

**Rollback trigger, pre-committed before go-live:** if field-level accuracy on the live sampled review falls below the agreed bar for two consecutive review cycles, or if any unresolved part number reaches the work-order system, drafting pauses and the process reverts to admin transcription. Named owner: the service-operations lead who owns the work-order process.

**Change control.** Prompt, schema, alias-table and catalogue-version changes are recorded and re-scored against the golden set before release. A catalogue update is a system change, not a data refresh.

### Delivery Approach

Quick-win quadrant with a modest service-operations budget, so the delivery shape is deliberately small: one build owner, part-time input from the service-desk admin (essential — they are the ground truth), and a service-operations sponsor who owns the rollback decision. Budget expectation is payback through warranty recovery; note that the ≈$40k/year rejected-claims figure is the team's attribution and has not been audited by finance, so the business case should be re-baselined during the pilot rather than treated as a validated return.

**Sequence:** inspect the data before building anything → assemble the golden set in parallel with the thin pipeline → score offline against the bar → shadow mode → limited release with sampled review → full rollout.

**Shadow mode specifics for this case:** the system drafts against real incoming voice notes overnight while the admin continues transcribing as normal the next morning. Drafts are compared silently to the admin's version. This yields live field-level accuracy at zero operational risk and, usefully, quantifies the admin-hours the system would actually save before anyone commits to the change.

**Limited release** puts the draft in front of a small volunteer group of technicians for same-visit confirmation. Their edit behaviour is the real test — a draft that is technically accurate but awkward to correct on a phone in a plant room will be abandoned regardless of score.

**Effort sizing is an estimate only.** The durations in the milestone table assume the historical note/work-order pairs are joinable and that the parts catalogue is available as a queryable table. If the archive turns out to hold only admin-retyped text and no original audio, the transcription component loses its tuning corpus and the timeline extends.

**What would stall this build:** an unjoinable historical corpus, a parts catalogue with no usable alias surface, or transcription quality so poor on real site audio that the draft costs more to correct than to write. Each is discoverable in the first phase, which is why the first phase is inspection.

### Integration Notes

- **Work-order system write path.** v1 should write only technician-confirmed output, via whatever API or import route the work-order system already supports. If no write API exists, the fallback is a confirmed draft the admin pastes — slower, but it still preserves the detail-loss fix, which is the actual value.
- **Capture point.** Prefer the existing recording habit over a new app. If technicians already dictate into a phone recorder or messaging channel, ingest from there; changing capture behaviour and introducing AI drafting at the same time confounds the evaluation.
- **Confirmation surface.** Mobile-first, offline-tolerant. Site visits happen in basements and plant rooms; a confirmation UI that requires connectivity at the moment of confirmation will push technicians back to next-morning workflow and dissolve the benefit.
- **Catalogue coupling.** Treat the parts catalogue as a live dependency with a version stamp on every generated summary. Superseded part numbers are a predictable failure mode for warranty claims.
- **Batch scheduling.** Latency is batch, so transcription and drafting can run on a schedule (e.g. shortly after each note arrives) rather than synchronously — but drafts must be ready before the technician leaves site if same-visit confirmation is to work. That timing constraint, not raw model speed, is the real requirement to validate.

## Data flows

**Voice note → confirmed work order (primary path):** Technician dictates voice note at end of site visit; audio queued with job reference → Speech-to-text produces transcript; raw audio reference retained for traceability → Transcript queried against parts catalogue lookup (name/alias/model match) via read-only tool interface → Transcript queried against vector index of historical note→work-order pairs, filtered by equipment and fault metadata → Grounded prompt composes structured draft against the fixed field schema → Deterministic part-number gate: every proposed part must resolve to a catalogue entry, else emitted as unverified candidate with pick-list → Draft presented to technician on-site for confirmation and edit → Confirmed output written to work-order system; edit delta logged as accuracy signal
**Reference corpus & catalogue preparation:** Inventory sources and confirm ownership plus access route for notes, work orders and catalogue → Manual inspection of ~50 note/work-order pairs to test joinability and real quality → Curate clean note→work-order pairs; discard uncertain linkages → Parse historical work orders into the target field schema → Chunk reference records at record/field-group level with equipment, fault and site-type metadata → Normalise parts catalogue into canonical numbers plus alias table harvested from historical notes → Embed and index reference corpus; publish catalogue lookup surface → Scripted refresh on the source's periodic update cadence, with version stamping
**Evaluation loop:** Admin adjudicates golden-set items covering routine, edge and hard cases toward 200 verified work orders → Candidate change runs against golden set → Structured fields scored by exact comparison; free-text fields scored by written rubric on a human sample → Optional LLM-as-judge only after judge–human agreement is measured on a subsample → Part-number fabrication counted separately as a hard gate → Failures classified as retrieval miss, transcription error, reasoning error, hallucinated detail or formatting error → Red-team findings added permanently to the golden set → Live edit deltas from confirmed work orders tracked per field for drift

## Milestones

- **Phase 0 — Data first contact** — Establish whether the historical notes, work orders and parts catalogue actually support the build, and lock the acceptance bar with the service-operations owner. _(~1–2 weeks (estimate))_. Exit: ~50 note/work-order pairs inspected by hand; joinability, presence of original audio, and part-recording format documented; parts catalogue confirmed queryable with a draft alias table; acceptance bar signed off unchanged (≥90% field-level accuracy on 200 admin-verified work orders, no fabricated part numbers).. Risk owner: Service-operations lead with the service-desk admin.
- **Phase 1 — Golden set & field schema** — Make accuracy measurable before making it good: define the field schema and build the first tranche of the verified evaluation set. _(~2 weeks (estimate))_. Exit: Field schema agreed with the admin and mapped onto historical work orders; first 50–100 admin-verified items scored-ready with rubric written for free-text fields; scoring harness runs end to end on placeholder outputs.. Risk owner: Build owner.
- **Phase 2 — Thin grounded pipeline** — Build the smallest version of the grounded-prompting pattern that can be scored: transcription, catalogue lookup, reference retrieval, schema-constrained composition, deterministic part gate. _(~3 weeks (estimate))_. Exit: Pipeline produces schema-valid drafts for all golden-set inputs; part-number gate enforced in code so no unresolved part can be emitted as a catalogue number; prompts, schema and retrieval config under version control.. Risk owner: Build owner.
- **Phase 3 — Offline evaluation to the bar** — Reach the acceptance bar offline and understand the failure distribution. _(~2–3 weeks (estimate))_. Exit: Golden set expanded to 200 admin-verified work orders; field-level accuracy reported per field and meeting ≥90%; zero unresolved part numbers emitted; failures classified by category; red-team cases (superseded parts, parts mentioned but unused, garbled audio, technician speculation) run and folded into the set.. Risk owner: Build owner with service-desk admin as adjudicator.
- **Phase 4 — Shadow mode on live notes** — Run silently against real incoming voice notes while the admin continues transcribing, and compare. _(~3–4 weeks (estimate))_. Exit: Live field-level accuracy measured against the admin's own transcriptions and holding at the bar across the shadow period; no unresolved part numbers reaching any output; rollback trigger and named owner recorded before any technician sees a draft; observed admin-hours saved recorded to re-baseline the business case.. Risk owner: Service-operations lead.
- **Phase 5 — Limited release with sampled review** — Put same-visit drafts in front of a small technician group and test whether confirmation actually works in the field. _(~4 weeks (estimate))_. Exit: Volunteer technicians confirming drafts on-site; per-field accuracy from sampled admin review still at the bar; edit-delta trend flat or improving; confirmation UI usable in low-connectivity site conditions; no fabricated part numbers observed in live output.. Risk owner: Service-operations lead.
- **Phase 6 — Full rollout and oversight taper** — Extend to all technicians and reduce review sampling only on evidence. _(ongoing (estimate))_. Exit: Acceptance bar held on live sampled review across the limited-release period before extension; sampling rate reductions recorded as explicit decisions with the accuracy evidence behind them; catalogue-version change control active; rollback trigger live and tested.. Risk owner: Service-operations lead.

## Independent critic audit

**Critic verdict:** SHIP WITH FIXES

**Load-bearing gaps**
- **The part-number gate does not actually satisfy the fabrication clause** — The gate only checks that an emitted number "resolve[s] to a catalogue entry". A model that emits a real catalogue number for a part that was never used passes the gate while still fabricating the field. The bar ("no fabricated part numbers, verified against the parts catalogue") needs a precision/recall metric on parts-used against the admin-verified reference — wrong-but-valid part numbers must be counted as failures, not just unresolvable strings. No milestone measures this.
- **No evaluation of the transcription layer independently** — Transcription is the single input to everything downstream and the plan itself anticipates "site-specific vocabulary problems (part nicknames, equipment models, accents, generator/compressor noise)", yet there is no WER/keyword-error baseline, no per-field attribution back to transcript quality, and no acceptance threshold. If field accuracy misses 90%, the plan cannot tell whether to fix prompting or capture.
- **No handling of audio retention / provenance policy failure** — Governance only says "Recording retention follows existing service-operations policy — confirm it covers audio, since the current process may treat voice notes as ephemeral." This is a discovery item with no owner, no phase, and no fallback. Traceability ("Every field links back to the transcript span") is a promised control that collapses if audio/transcripts cannot legally be retained; that dependency should be resolved in Phase 0.
- **No abort/refine path if Phase 0 or Phase 3 fails** — The plan names stalling conditions ("an unjoinable historical corpus, a parts catalogue with no usable alias surface, or transcription quality so poor...") but every milestone exit criterion is written as success. There is no defined decision point that returns the case to REFINE or kills the build, and refineGate is null.

**Top fixes**
- Redefine the fabrication metric: measure parts-used precision/recall against the admin-verified reference so valid-but-incorrect catalogue numbers count as failures, and add that metric to the Phase 3 and Phase 5 exit criteria — the deterministic gate alone does not meet the bar.
- Fix the shadow-mode ground truth: score Phase 4 against admin-verified work orders (the bar's reference), not against the next-morning transcription the project exists to replace; if same-day admin verification isn't feasible, state that shadow accuracy is a proxy only and cannot discharge the bar.
- Delete the "zero operational risk" and "single highest-leverage artefact" claims, soften "no unresolved part can be emitted" to what the code actually enforces, and move rollback-trigger commitment plus audio-retention confirmation into Phase 0 with a named owner and an explicit abort/refine path.

**Overclaims flagged**
- "This yields live field-level accuracy at zero operational risk" — shadow mode still consumes admin time, retains customer-sensitive audio, and its accuracy figure is measured against a reference the plan elsewhere calls lossy; risk is low, not zero.
- "The model is never the authority on a part number; the catalogue is" — true only for existence, not for correctness of selection; as written it implies the fabrication risk is eliminated.
- "This alias table is the single highest-leverage artefact in the build" — asserted as fact before any data has been inspected; the plan's own Phase 0 exists precisely because alias harvestability is unverified (it appears as an assumption).
- "Batch latency ... removes most performance pressure" sits awkwardly beside "drafts must be ready before the technician leaves site" — a tight, unquantified turnaround requirement is being described as no pressure.

**Fabrication scan**
- `This yields live field-level accuracy at zero operational risk` → must-remove
- `part-number gate enforced in code so no unresolved part can be emitted as a catalogue number` → must-label
- `This alias table is the single highest-leverage artefact in the build` → must-label
- `Pull a sample of roughly 50 note/work-order pairs and read them by hand` → ok
- `~1–2 weeks (estimate)` → ok
- `the ≈$40k/year rejected-claims figure is the team's attribution and has not been audited by finance` → ok

**Consistency issues**
- Shadow-mode ground truth is circular: Phase 4 measures "Live field-level accuracy measured against the admin's own transcriptions", but the grounding problem statement is that the admin's next-morning transcription is exactly where "detail is lost overnight". The acceptance bar is defined against "admin-verified work orders", not against the unverified daily transcription — the plan silently swaps the reference standard.
- Rollback trigger timing conflicts: Governance says the trigger is "pre-committed before go-live", yet Phase 4's exit criterion only requires it "recorded before any technician sees a draft" — i.e. the shadow run against live customer notes can start with no trigger and no named owner in place.
- A speech-to-text component is introduced as a core pipeline stage ("Transcription", "transcription error" as a failure category) but no acceptance criterion, metric or exit gate anywhere covers transcription quality on its own; it only appears folded into field accuracy, so a transcription regression is indistinguishable from a prompting regression at the gate.
- Phase 3 requires "Golden set expanded to 200 admin-verified work orders" and Phase 1 requires the admin to adjudicate the first 50–100, but the assumption list concedes admin capacity is unproven ("Assumes the service-desk admin has capacity to adjudicate 200 golden-set work orders alongside existing duties") with no fallback path if it isn't — the bar's denominator is unprotected.

**Acceptance bar is the spine:** yes — The bar is quoted verbatim in the summary, Evaluation section and Phase 0 sign-off, and it is the literal exit criterion of Phases 3–6 ("field-level accuracy reported per field and meeting ≥90%; zero unresolved part numbers emitted"; "Acceptance bar held on live sampled review").
**Verdict integrity:** pass — Plan states BUILD, matching the grounding verdict, keeps the acceptance bar verbatim ("The bar, unchanged"), and actively resists a rosier case by flagging the $40k figure as unaudited and recommending re-baselining. No drift detected.
